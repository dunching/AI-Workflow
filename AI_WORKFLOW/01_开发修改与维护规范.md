# 开发、修改与维护规范

## 默认推进方式

先厘清事实和实现方案，再连续完成完整功能边界的主体框架与生产接入，随后集中验证、归并修复和验收。已有有效方案、代码和证据优先复用。

| 任务类型 | 推进顺序 |
| --- | --- |
| 新功能、架构改造 | 确认目标与现状 → 实现方案 → 主体框架和生产接入 → 集中测试补缺 → 验收 |
| 缺陷修改 | 确认故障与因果 → 同一根因归并修复 → 精准回归 → 必要集成检查 |
| 日常维护 | 确认影响 → 局部或批量修改 → 受影响范围内的检查 |

不把所有任务都套成逐条测试驱动；也不为减少构建次数合并无关功能。用户已选定的方法按[工作流入口](00_工作流入口.md)执行。

## 一、先给方案，明确交付边界

方案覆盖以下决定，保持足够具体，不扩写成操作流水账：

- 目标、交付阶段、真实用户或消费者、本批最小完整行为、验收条件和明确不做的内容；关键约束按工作流入口区分来源。
- 当前真实调用链、数据来源、字段所有权、读取版本、写入边界和提交点。
- 接口、配置、协议版本、工厂、生命周期、编码与恢复的影响。
- 拟修改文件、必要调用方、实际消费入口，以及现有实现和工具的复用方式。
- 按可独立验收的行为边界划分批次，说明每批交付和依赖；事务形态是待审查的实现选择，不默认冻结旧结构。
- 必要验证、成本预算、进展检查点及停止反复试错的条件；时间估计明确标为估计。

根据已明确的交付阶段推进，不反复要求用户选择模式：快速原型优先接通生产闭环、验证关键未知；正式交付覆盖本次实际需要的可靠性和兼容。不得自动把原型升级为通用框架，也不得把正式任务降级为原型。
架构方案应解释主体如何贯通，不写成大量“新增一条测试、改一个函数、完整构建一次”的步骤。
当前任务已有明确授权时，在该范围内继续；不重复请求同一项授权。

## 二、按完整功能边界连续实现

- 单批保持单一目的，同时完成生产实现、调用方、适配、配置、编码恢复和真实消费者的必要修改。
- 同一接口的生产代码和测试夹具使用同一份合同，集中迁移必要版本和调用方式。
- 完整主体指本批选定范围的入口、实现和真实消费者接通，不要求补齐未来模块、所有泛化能力或未承诺的兼容版本。接口、空任务、模拟输出或只有测试能调用的实现不算生产接入。
- 运动、业务、网络等模块明确各自读写集合、借用寿命、私有缓存和结果合并，不复制另一份权威来规避边界问题。
- 执行时序或并行改造复用同一计算路径和有效串行参考；先明确语义，再实现任务依赖。不同完成顺序不能改变输入版本或提交结果。
- 已有参考可直接复用，不因无关旧用例未全绿而阻断主体编写。直接破坏本批集成、数据完整性或生命周期的问题及时处理。
- 不为保留旧形式叠加永久双实现、空包装或无用抽象；不擅自改变已批准的算法、业务负载和验收要求。

## 三、实现期间保留基础检查

- 做必要的语法、编译、UHT / UBT 和最小启动检查，尽早拦截基础接口及启动错误。
- 基础检查用于支持持续实施，不把每个局部的完整回归作为继续写主体的前置，也不把长时间完全不验证当作提速。
- 不默认清理缓存后全量重编；反射、生成代码、模块依赖和资源变更要做对应的真实检查。
- 不因每条断言、单个文件或可归并的日志修正分别启动完整构建。
- 基础检查通过不能替代链接、运行或最终验收结论。

## 四、主体接通后集中验证

- 依据本批验收目标，集中运行功能反例和受影响回归；按[功能验证与构建](04_功能验证与构建.md)选层级。
- UE 独立纯逻辑测试优先使用 UE LLT，复用其测试模块、构建、断言与报告机制；不默认新增自写 main()、手动计数断言及编译脚本组成的独立测试入口。
- 验证前集中检查测试输入、初始状态、恢复资格、版本、参数、渲染条件和断言，确认目标行为确实能够执行。
- 不把测试框架迁移、重放工具扩建或所有历史测试重写设为功能开发前置。
- 测试和验证方法随任务需要选择，不借流程要求更改生产语义来取得通过。

## 五、按共同原因修复，限制返工循环

- 失败先区分生产缺陷、夹具错误、旧语义预期、构建问题、环境问题和未知原因。
- 将同一接口或共同原因下已确认的问题归并修复，再集中复验。
- 保留原始失败、有效程序、输入和已有结论；不能删真实反例、放宽有效安全要求或改变负载掩盖问题。冗余检查的等价简化按[功能验证与构建](04_功能验证与构建.md)处理，不将旧检查实现本身当作验收目标。
- 连续昂贵验证未缩小故障范围，或到了检查点仍没有主体推进，按[返工熔断与推进复盘](11_返工熔断与推进复盘.md)调整方法。
- 不通过不断换失败用例、增加诊断文件或改名任务延续同一轮无进展返工。

## 六、围绕实际差异审查与汇报

- 审查完整批次的接口、所有权、生命周期、恢复、提交和真实消费路径。
- 先审本批实际增量，复用仍有效的检查结论，不无依据重读全部上下文、重复交接或重复审查。
- 问题按严重程度说明影响与证据，引用实际文件和行号；没有发现也明确验证范围和剩余风险。
- 进度报告接通的功能、已证明的行为、当前阻断和剩余交付。
- 测试数和改动文件数是辅助信息，不折算成功能完成率；实现、正确性与性能分别报告。

## 七、轻量交接与最终验收

- 保持一个当前方案和一份简明当前状态；项目要求多份状态文件时相互引用，避免复制多套同等权威。
- 历史记录单独保存，在里程碑、关键决策或交接时更新状态和证据索引。
- 压缩恢复核对当前状态、相关差异和事实源；出现矛盾再扩大阅读。
- 功能收口后按项目规定格式化并检查，冻结最终验证输入，再执行最终构建和必要回归。
- 验证期间不修改受冻结范围内的源码、工具、配置、资源或输入。失败修复在终态后重开候选，并重新确认受影响结论。
- 不混用不同源码、引擎、程序或输入的结果；无新修改和覆盖缺口时，不重复已有效的验证。

## 实施约束

- UE 开发按 [UE 规则路由](../profiles/unreal/README.md)确认随包默认规范、项目覆盖和实际格式化配置；已可靠加载且未变化的内容沿用，缺失或变化时补读。非 UE 不加载该 profile。
- 遵守项目编码风格、目录与命名，不顺手大改无关代码，不覆盖他人未提交修改。默认复用既有 API 以降低影响，但本批内部接口可以审查替换；涉及外部消费者或兼容承诺时明确迁移。
- 注释解释意图、生命周期和非显然边界，不重复描述代码表面含义。
- 结构化数据优先使用对应解析器或项目 API。接口或中间层若迫使重复扫描、复制或维护多份状态，先审查能否删除、合并或缩窄，再决定缓存和适配；新增抽象应有实际收益。
- 新增防御、回退和兼容路径须对应本批实际支持的输入、消费者或失败边界，不只为“以后可能需要”建设。无效或不支持的状态明确失败，不静默吞错。
- 重复验证同一保证时，指出两次之间可能使其失效的写者、结构变化或外部输入。已由所有权、阶段隔离或输入边界保证的条件优先在适当边界检查；保留必要的输入、生命周期、并发内存安全和数据完整性要求。
- 同一组共享文件只有一个明确写入者。只读分析与审查可以独立安排；工作树和协作方式服从用户授权。
- 视觉、动画和实际表现需要相应画面证据，按[可视化流程验证](05_可视化流程验证.md)执行。
- 共享流程不记录项目待办；普通项目维护不擅自修改本工作流。
