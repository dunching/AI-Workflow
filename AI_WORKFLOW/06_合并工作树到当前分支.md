# 合并工作树到当前分支

## 适用与授权

仅在用户要求整合已有工作树或分支时使用，不因该文档存在就创建工作树或执行 Git 操作。
项目禁止并行工作树时，不自动启用本流程。
规则入口见[工作流入口](00_工作流入口.md)；已有明确整合授权在其范围内持续有效。

## 操作前事实

定向核对并简要说明：

- 当前与来源工作树的真实路径、Git 归属和分支。
- git worktree list 与两侧 git status --short。
- 来源、目标的提交关系和上游状态。
- 未提交修改、子模块、忽略资源及需要保全的证据。
- 采用的合并方式、文件边界和已知冲突风险。

路径、分支或未提交内容的处置不清楚时先澄清。不能擅自提交、覆盖或丢弃这些内容。

## 合并策略

- 整合 Git 历史，默认按已批准方案使用 git merge。
- 只需特定提交或来源含无关内容时，按授权使用 git cherry-pick。
- 不通过文件夹复制替代历史合并。
- 不默认 rebase、reset --hard、强制推送、覆盖检出或破坏性清理。
- 已授权正常合并不为每个命令再次确认；新增提交、推送、清理或破坏性处置需要相应授权。

## 冲突

- 记录冲突文件和相关两侧意图，保留用户改动与证据。
- 授权覆盖且语义可确认的文本冲突可按方案处理；含义不清或改变架构时先取得决定。
- .uasset、.umap 等二进制资产不伪造语义合并，说明两侧差异并确认选择或编辑器处理方式。
- 不未经允许中止合并、强行选一侧或丢弃工作树。

## 合并后验证与交付

1. 核对实际提交关系、工作区和子模块状态。
2. 仅对合并造成的相关代码、资源或配置变化选择必要检查。
3. 复用仍适用的已有运行结论，不因只读元数据检查重跑整个工程。
4. 报告来源、目标、实际命令、冲突处置、验证结果和未提交内容。
5. 未获推送或清理授权时，不自动发布或删除工作树。

本流程执行期间仍遵守项目源码冻结、引擎身份和证据保全要求。
